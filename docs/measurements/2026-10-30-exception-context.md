## 修改原因与实现

上一轮同课题完整成功运行用了 34 次调用，其中 25 次发生在首轮之后，
四个任务均修正过生成测试。公共前缀已经稳定，但 Opus 命中率仍为 38.27%。
本轮处理两个具体问题：缓存格式切换，以及缺少旧代码导致的测试设计误判。

- 测试设计节点从规划基线读取本任务、声明依赖及其导入依赖的旧源码，
  复用 Index 和依赖图；在启动 builder 前固定读取结果。新实现和隐藏验收不进入输入。
  这些内容放在任务段，保留 DSF 公共前缀，不压缩原始需求或降低 1M 窗口容量。
- `review` 与 `thicken` 共用 `EXCEPTION_SCHEMA` 和原始需求上下文。
  操作指令放在动态消息，运行时代码继续校验操作边界：契约补充不能修改测试，
  测试复核不能顺便替换契约。没有把所有规划、构建、复核合并成一个大 schema。
- 修复上下文去重使用文件名却收到 `path::symbol` 键的问题。
  整文件、类和方法按覆盖关系去重；兄弟符号、其他文件和仅有签名目录的实现仍保留。
  完整 owned source 已包含的补读和推导符号不重复发送。

复用 `Index.read/at`、依赖闭包、`render_files`、`ContextPrompt`、
`object_schema`、`serialization.dumps` 和原用量账本。无新增依赖或后台服务。
分类器独立分支的文件未修改。

## 第二轮：冻结测试错误直接复核并复用代码

首次实测仍出现冻结测试自身的 UnboundLocalError，调度器却先重试实现再调用 Opus patch。
新增 `fixture_error` 复用现有 `FRAME` / `frame_path`：只有 unittest ERROR 的最内层帧
确实属于冻结测试、异常为 NameError 或 UnboundLocalError，才返回复核证据。
断言失败、实现内部异常、AttributeError/ImportError 不走此分流。

此路径仅触发原有独立复审，不自动改测试，仍遵守每任务最多三次复审及不重复复审被驳回版本的约束。
保留已有 `pending_candidate`，测试修正后通过原有 `_reuse_candidate` 重放候选代码，
重新执行验证及合并门，不再调用 builder 重新生成相同实现。
已保存候选的执行路径也进入同一 Signal 处理逻辑，支持新测试版本再次出现独立 fixture 错误。

针对性验证中，连续一次或两次纠错均只生成一次 DSF 实现，产生相应的候选复用事件；
非法跨操作响应、候选身份不符和不应分流的异常也保留验证。
