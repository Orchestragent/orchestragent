# Claude 缓存边界：修改动态问题时复用公共源码

## 已验证的结论

把公共源码与动态问题拼成一条用户消息，会让修改末尾问题触发大段缓存重写。通过原生 Claude Code 的 `--append-system-prompt-file` 把公共上下文放入独立系统区段，本次小型对照中，变化问题那一轮的缓存读取命中率从 **14.5% 提高至 94.3%**。这是机制验证，不是整项目性能或质量成绩。

环境：Claude Code `2.1.280`，原生订阅 `claude-opus-5-5`、medium effort；禁用工具、MCP 和会话持久化；没有 API 调用、账号切换、TTL 强制修改或保活调用。脚本 [orch_claude_cache_probe.py](../../scripts/orch_claude_cache_probe.py) 在运行前提交；主对照 engine 为 `d6314aa`。后续 `dd7bede` 对齐运行事件与账本的上下文边界指纹，不改变实测的 native 请求机制。

## 方法与结果

两组使用相同源码、模型、结构化输出 schema 和 A、A、B、B 顺序。问题 A 查询 `PARK`，B 查询 `MAX_SAMPLES`；公共源码完全一致。每组四次调用，顺序执行 flat 后 context。没有清理厂商缓存；不能假设两组初始冷热相同。

下表比较每组第 3 次调用，即已有 A 缓存后第一次询问 B：

| 指标 | 原单条消息 flat | 公共上下文分块 context |
|---|---:|---:|
| 总输入 token（普通输入 + 缓存读写） | 12,913 | 12,970 |
| 缓存读取 token | 1,870 | 12,227 |
| 缓存写入 token | 11,041 | 741 |
| 未缓存输入（含写入） | **11,043** | **743** |
| 缓存读取命中率 | **14.5%** | **94.3%** |
| 输出 token | 52 | 52 |
| CLI API 等价估价 | US$0.089750 | US$0.009421 |

公共上下文分块减少了该轮约 **93.3%** 的未缓存输入。美元数是 CLI 的 API 等价估价，不是订阅之外的实付账单。全组含冷启动的命中率和单次热缓存命中率不能混用；原始报告保留每次用量与时间。

这一小对照的 context 组四次答案均符合字段值约定。flat 第一轮把答案包装成了字段内的 JSON 字符串，严格格式验证失败，后三轮通过；这个问常量的课题不构成代码质量评测。不存在未结算推理或因未知结果重发请求。

## 被否定的目录假设

最初依据官方文档怀疑随机工作目录破坏前缀，尝试固定空目录。先导实验却显示：随机目录的完全重复请求也能约 98.5% 命中；固定目录还能读取随机目录组留下的缓存。因此不能把当前 safe/restricted 路径的低命中主要归因于目录，更不能比较两组受交叉预热影响的总命中率后宣称目录有效。固定目录改动已撤回，恢复每调用独立临时目录与清理行为。

先导有一次 2 调用的提前停止（严格答案格式不符），之后完成 8 调用目录对照，再完成本报告的 8 调用分块对照。共 18 调用；三份原始报告全部保留，不隐藏反例或格式不符结果。

## 接入与 DSF 稳定性

- 新增轻量 `ContextPrompt(str)`，只携带稳定上下文与动态部分的边界。普通文本调用接口保持兼容，其他执行器仍能看到完整文本；不引入 Redis、会话服务或缓存数据库。
- Claude 边界规划、补丁修复、测试争议审查、契约补充已接入。普通完整规划和重新拆分尚未切换；不同 schema、任务与版本仍可能产生冷缓存，不能把本次 94.3% 当作全局承诺。
- 运行账本对上下文边界参与请求哈希计算，并记录实际公共上下文指纹；原有用量归一化、状态机、预算和未结算处理继续复用。
- DSF 对补丁/协议等未进入有效测试的失败，保留单次修正机会，但不再盲目扩成四个并行候选；合法代码的测试失败仍可采样。提示词明确失败 diff 并未应用，搜索片段必须取自当前文件。
- DSF 改动已有确定性调度回归，尚未做新的真实项目失败率对照。此前 Boltons 8/8 是上一版本的结果，本报告不将它冒充为本次缓存改动后的端到端验收。
