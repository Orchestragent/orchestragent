# Boltons：工具型单 agent 与 Orch 集群实测

日期：2026-10-30，执行环境：同一台 Mac。结论：**这一题单 agent 完整交付；Orch 未完整交付，不能宣称更快或更省。**

## 固定课题与比较口径

- 上游：[mahmoud/boltons](https://github.com/mahmoud/boltons)，提交 `d31d821d56c8f7756af9c30a864077f2e5855321`。
- 测量脚本统计 `boltons/*.py`：30 个文件、17,718 行；这是已有中型仓库中的四模块改动，不代表大型分布式系统能力。
- 课题：[spec.md](../../examples/orch-bench/boltons-checkpoint/spec.md)：在已有队列、JSONL、原子保存模块上实现可断点恢复、去重的任务队列。这是实验性需求，不是上游已接受的 issue。
- 两方使用同一份原始需求、上游提交、固定 pytest 环境和 [8 项隐藏验收](../../examples/orch-bench/boltons-checkpoint/test_acceptance.py)。隐藏验收没有提供给模型，也没有把其失败信息反馈给模型修补实现。
- 上游原始沙箱基线：618 passed、3 failed、22 subtests passed。3 个失败来自沙箱禁止子进程或 TCP 监听；用已提交的固定 overlay 显式跳过后：618 passed、3 skipped、22 subtests passed。未修改原测试；没有运行 doctest。
- 共同实验基线：`f088146c640d7fda205d9c444a620d1941374b0a`。沙箱仍禁止网络、主目录读取和子进程。
- 单 agent：原生订阅 Opus 5.5，effort=high，独立会话；Read/Edit/Write/Glob/Grep/Bash 工具，可调用固定沙箱测试命令，无委派工具。不是 JSON-only 的单次模型模拟。
- Orch：Opus 5.5/high 决定边界，DSF 实现；Jev off。新路径把相关索引放入最多 12 KB 的地图，DSF 按任务并行设计冻结测试，再走现有调度、验证、修复和合并流程。
- 单 agent 原生进程上限 1,200 秒。Orch 先因试跑调用次数上限暂停，再从同一检查点续跑，累计活动窗口上限 1,200 秒。未手工修改模型实现或集群测试。下面同时报告活动时间与包含人为暂停的经过时间。
- 串行开展两个主对照，避免同时争用 Opus。未清空厂商缓存，试跑顺序和缓存冷热不同；每条路线只有一个完整课题样本，不能外推稳定倍数优势。

## 重试、重复消耗与停点

- 单 agent：29 条可观察助手消息，52 次工具请求；3 次实际沙箱测试均通过，另有 1 次工具错误。CLI 提供整次会话聚合用量，没有独立的内部模型重试计数；不能据此宣布“零重试”。
- Orch：26 条调用回执，其中 1 条在本地被预算准入拦截；20 条 DSF 回执，6 条 Opus 回执（含该拦截）。单 agent 的一次 CLI 会话与一次 Orch 叶子调用不是同一统计单位。
- 6 次任务失败事件、2 次冻结测试自动纠错。第 2 次及以后尝试的调用共计 155,542 token；其中包括必要审查和成功修复，不能全部贴成浪费。
- 完全相同请求哈希重提 1 次：前次是本地预算拦截，后次真正执行，共 17,212 已报告 token；**不是两次已付费推理的证据**。
- DSF 缓存读取命中率 61.27%；集群中 Opus 为 10.47%。测试设计分片 V2 命中率 35.67%；较早 V1 为 4.19%，但跨轮次缓存冷热不同，不能全归因于前缀改动。
- 同时处于生成阶段的任务数峰值 3、验证槽峰值 5；每任务还可能展开多个采样，且包含本地等待，不等于厂商实际同时推理数。通讯、状态更新、合并和暂停走本地代码，没有用模型轮询进度。
- T-001、T-002 各经历 5 次任务尝试，T-003 首次完成。T-004 发送一次 `NEED_FILES`，请求三个完整依赖文件：`boltons/queueutils.py`、`boltons/jsonutils.py`、`boltons/fileutils.py`；补入后必需上下文超过 **39,919 字节**，在再发模型之前 PARKED。
- 两份自生成测试有真实错误：priority_key 的参数语义被误解；JSONL 测试硬编码了错误偏移，还搜索不存在的字节串。自动审查修正后，前两个模块才通过。没有人工给它改答案。
- 最终无未结算的集群回执；没有因这个停点反复发送超长上下文。

## 实现与局限

本次实现复用版本化 Index/AST、依赖闭包、边界校验/合并、冻结测试、沙箱、调用账本和预算准入；CLI 新入口为 `plan --distributed --test-jobs 4`，保留原规划作为对照。并行测试分片限定文件与需求归属；局部格式失败只重试该分片；共同上下文置于稳定前缀；已结算 JSON 截断可重试，未知超时不自动重放。另修复真实仓库发现的 pytest 子测试重复计数，以及原生 `timed_out` 的未结算分类。

本次没有实现跨进程规划分片续传，也没有边规划边启动实现；分工规划仍是显式实验入口。

单 agent 评测器最初误把普通文档改动当成受保护配置，已修正并在**同一结果提交、相同隐藏验收摘要**上离线复核；修正前后实现均为 8/8。另清理了测试工具遗留的控制器临时目录。未修改 agent 代码、未重跑模型、未泄露隐藏验收。这些是评测器修正，保留了修正前报告。

下一步应先解决三件具体问题：

1. 给测试设计节点提供相关既有 API 的源码/文档切片，避免只凭签名猜语义；对测试夹具本身的错误提前分流。
2. `NEED_FILES` 超限时按符号或分批提供依赖上下文，让集成节点能继续工作，而不是一次塞入三个全文件。
3. 明显相同的测试失败先检查契约/测试，再决定多样本重试，避免在错误裁判上消耗多个候选。

复跑应继续使用同一单 agent 工件、需求和隐藏验收，先达到 8/8，再比较端到端时间与消耗；当前数据不能支持“集群比单体强”的结论。
