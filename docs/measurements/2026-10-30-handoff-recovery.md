# 控制链路、恢复与对账报告

实现：`cc1e0a70454a99a9a9c6a7a4a5802acb5356b84f`。本轮只有本地代码与 CLI，未推送或部署，
没有真实模型/API 调用，也没有修改授权预算或清除历史费用预留。

## 核心变化

- **工件交接代替重新生成**：保存候选 commit，动态导入依赖就绪后重放、重新验证再合并。
  控制器重建后也能复用候选；正常依赖等待不再要求模型重新写同一份代码。
- **事务性控制状态**：依赖加边、候选等待与重试授权在数据库事务内确认。复用原有 DAG
  检查，两个节点并发互相依赖时最多接受一个方向；重复交接不重复改变状态。
- **按数据类型采用一致性**：控制状态事务化、合并串行化；代码以不可变 commit 传递；
  索引/上下文固定 revision/blob；缓存与展示只是可滞后的观测，不决定合并正确性。
- **不把未知当失败重发**：请求已发出但缺回执，或取消/超时后无法证明结果，停放并保留
  未知费用。`reconcile` 只读检查；显式 `retry --ack-unknown` 才授权可能重复的调用。
- **停止无进展和资源空转**：重复索取已提供内容停止；并行样本共享同一次补读。取消能
  退出限速/验证排队；调度器异常停止派发，恢复重建槽位。深 DAG 不再递归排序。
- **统一拒绝判断**：复用 DSH 既有的明确拒绝列表，直连、预算释放和对账使用同一规则。
  429 等明确拒绝可正常退避；408、未知 4xx、5xx 不再被当作已证明零消费。

复用：`Index` / AST 导入与接口分析、原有 DAG 检查、`OrchState` 状态机与事务、
`Ledger` 回执、Git 工作树与验证闸门、`TokenBucket`、共享 JSON 序列化。账本读取抽出
事务内入口，恢复决策不再需要另造查询或序列化工具。

## 故障边界证据

| 场景 | 验证结果 |
| --- | --- |
| 动态依赖尚未合入；交接后重建控制器 | 三个 builder 各调用一次；恢复直接复用候选，完成后审计无发现 |
| 两个节点同时追加互相依赖的边 | 只提交一个方向，剩余图无环 |
| 四个样本从旧快照请求同一文件 | 只消耗一轮补读；收到内容后再次索取判定无进展 |
| 崩溃留下 pending 回执，无候选 | 恢复后 PARKED，不发新模型请求；未确认费用保持未知 |
| 请求发出后取消，再次 resume | 不隐式重发；需要明确重试授权 |
| 候选不存在、契约/路由不匹配 | PARKED，不自动再生成 |
| 调度器 worker 异常 | 暂停并取消派发；恢复不遗留占满的槽位 |
| 1,500 层依赖图 | 排序不触发递归栈溢出 |
| 验证队列取消、限速桶已有额度时取消 | 不启动新的工作，不错误释放其他任务的槽位 |
| 408 与 429 | 前者保留未知敞口；后者按明确拒绝处理 |

最终完整检查：**1,347 passed、5 skipped**；Ruff、mypy 通过。重复工具扫描确认共享
序列化、DAG 检查和拒绝状态列表均只有一份。上述恢复测试是故障注入和控制器重建，
不是物理断电实验。

## 使用与范围

```sh
scripts/orch --repo /path/to/project reconcile --run RUN_ID --json
scripts/orch --repo /path/to/project resume RUN_ID
# 只有接受未知请求可能仍被计费，才显式授权重试：
scripts/orch --repo /path/to/project retry T-001 --run RUN_ID --ack-unknown
```

`reconcile` 是非原子观测，不清账、不改状态；运行中的瞬时 HEAD 差异不能直接判为损坏。
损坏/过期候选需明确 `--discard-candidate` 才重新生成。

已验证边界是当前**单机、单 run 控制器与内置传输**。模型响应到候选落盘前的崩溃窗口
不能凭空重建输出；第三方 Caller/Runner 必须遵守取消和有限超时契约，线程执行器不能
强杀任意不合作的 Python 插件。跨机网络分区、主控选举与 fencing 尚未实现，不能将
本轮结果解读为这些分布式保证，也不承诺厂商推理 exactly-once。
