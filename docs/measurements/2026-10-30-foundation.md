# 候选有效性与恢复边界修复

引擎：`b8a6cd704aed70683954d325277b85c7fb771416`。
本轮只修底层并回放已有工件，没有新调用 Opus、DSF 或 Jev，没有新的 API 费用。

根因不是缺少 AST，而是 AST、失败分类和持久恢复之间没有统一执行边界：
签名集合会掩盖同名覆盖；残留占位体直到运行时才暴露，却被当成行为错误进入采样；
测试变更后只保留错误摘要，已有代码容易被重新生成；测试计划与任务状态分开写入。

## 已改动的执行边界

- 先检查全部编辑可编译，再写文件。候选从不可变 Git commit 读取，用已有
  `codeindex.definitions` / `orch_index.is_stub` 检查新增同名定义、冻结具体接口的占位体、
  已有实现退化。`is_stub` 判断异常 AST，不再匹配字符串中的 NotImplementedError。
- 结构错误在行为测试之前拒绝，反馈符号及行号。只有行为测试失败可以采样；
  决策器提出已用、未知或不符合资格的恢复动作时，记录原因并采用确定性阶梯。
- 行为失败的候选以 Git SHA 保存。确认测试错误之后先验证候选的来源、契约、模型、
  单父提交与所有权，再重放已有代码；DSF 和 Opus 同样处理，不需要模型转述代码。
  丢失或过期的历史失败候选会记录丢弃原因。正常恢复遇到坏的待验候选仍会停放，
  不改变未知费用必须人工确认的规则。
- 修改冻结测试时，计划、已验证 HEAD、待验候选、任务状态与纠错事件同事务提交。
  写入中途失败会回滚数据库与集成分支；恢复后重新验证，不沿用旧测试结果。

复用 `Index.read`、`definitions`、`is_stub`、traceback 匹配器、原有候选重放/合并门、
`Store.transaction`、`integration_change` 和 `serialization.dumps`。
新增领域检查 `implementation_errors`，将原 `fixture_error` 扩为 `diagnose_failure`，
并集中候选身份检查；没有引入通用框架、依赖或新的序列化工具。
