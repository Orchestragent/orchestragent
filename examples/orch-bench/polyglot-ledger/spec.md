# Ledger: a Go service exports a canonical ledger; a TypeScript client reads and reconciles it

The repository has a Go module in `api/` (module `example.com/ledger`, package `ledger` in
`api/ledger`) and a TypeScript package in `web/` (vitest, strict tsconfig). Implement the
requirements below in those two components. Add tests in each component.

R1. In Go package `ledger`: `type Entry struct { Date string; Account string; AmountCents int64; Memo string }` and `func ParseCSV(r io.Reader) ([]Entry, error)`. The input is CSV (encoding/csv rules, so quoted fields may contain commas and quotes) whose first line is exactly the header `date,account,amount_cents,memo`. Every following row has exactly four fields: `date` is `YYYY-MM-DD` and a real calendar date; `account` is non-empty and has no leading or trailing whitespace; `amount_cents` is a base-10 integer with an optional leading `-` (no `+`, no spaces, no leading zeros except the number `0` itself) that fits in int64; `memo` is any string, possibly empty. Rows keep their input order. Any violation, including a missing or different header and a wrong number of fields, returns a nil slice and an error whose message starts with `line N: `, where N is the 1-based line number of the offending line (the header is line 1). Empty input is an error starting with `line 1: `.

R2. `func Balances(entries []Entry) map[string]int64` returns the sum of `AmountCents` per account. An account is present exactly when it has at least one entry, including when its sum is zero. The input is not modified.

R3. `func ExportJSON(entries []Entry) ([]byte, error)` returns canonical JSON with no insignificant whitespace and no trailing newline: the object `{"balances":{...},"entries":[...],"version":1}` with its keys in exactly that order. `balances` maps each account (keys sorted by byte order) to its R2 sum as a JSON integer. `entries` keeps input order; each entry is an object with keys in exactly the order `account`, `amount_cents`, `date`, `memo`. Strings are escaped as Go's encoding/json does with HTML escaping disabled. If any entry would fail R1's field rules, it returns nil and an error naming the entry's 0-based index (`entry 3: ...`).

R4. In TypeScript, `web/src/ledger.ts` exports `interface Entry { date: string; account: string; amountCents: number; memo: string }`, `interface Ledger { version: 1; entries: Entry[]; balances: Record<string, number> }` and `function parseExport(json: string): Ledger`. It reads the R3 format: the top-level object has exactly the keys `balances`, `entries` and `version` (in any order); `version` is the number 1; every entry has exactly the keys `account`, `amount_cents`, `date`, `memo`, with values obeying R1's field rules (`amount_cents` a safe integer); and `balances` has exactly the accounts of the entries, each equal to that account's sum. Returned entries use `amountCents`, in input order. Any violation, including invalid JSON, throws an `Error` whose message starts with `invalid ledger: `.

R5. `web/src/ledger.ts` exports `function formatCents(cents: number, currency: "USD" | "EUR"): string`. `cents` must be a safe integer, otherwise it throws a `RangeError`; any other currency also throws a `RangeError`. USD: `$1,234.56`, `-$1,234.56`, `$0.05`, `$0.00` (comma thousands separators). EUR: `1.234,56 €`, `-1.234,56 €`, `0,05 €` (dot thousands separators, comma decimal separator, one regular space before `€`).

R6. `web/src/ledger.ts` exports `function reconcile(service: Ledger, local: Entry[]): { missing: Entry[]; extra: Entry[]; changed: { service: Entry; local: Entry }[] }`. Entries are matched by the key (date, account, memo). `missing` lists service entries with no local entry of the same key; `extra` lists local entries with no service entry of the same key; `changed` lists pairs with the same key but different `amountCents`. If a key occurs more than once on the same side, it throws an `Error` whose message starts with `duplicate key: `. Each output array is sorted by date, then account, then memo (UTF-16 code-unit order; `changed` by its service entry). The inputs are not modified.

R7. The two components agree: for any entries that R1 accepts, `parseExport` accepts exactly the bytes `ExportJSON` returns for them, and the parsed entries equal the original entries field by field, in order.
